## 前回F1〜F8との対応

### F1 / F5 / F6 — 自分で配置を作り、相手の妨害後も打つ

`journey.js:createJourney / playJourneyMove / applyJourneyReply` は回答表から再生する教材ではない。空盤の任意の合法黒着手を受理し、appの`journeyReply`が実エンジンの白着手を渡し、次の黒を再び本人に要求する。五連が成立するまで本人の手を自動入力しない。固定白初手は`openingOverride`として区別する。

具体例は `J8 A1 H10 C1 H8 I8`。黒が作った二方向の一方を白I8が閉じ、本人のH9で`switch-direction`が生じる。白がH9なら残る方向が変わり、I8が候補になる。B12など別の静かな方針は`unknown`であり、証明なく負けにしない。さらにH11、白H7、H12まで本人が打てば五連になる。この工程は前回の「既成終盤を解くだけ」からの実質的な改善である。

`previewJourneyMove`は仮置きの比較であり、盤・journal・達成を変更しない。支援付きbuild/defendと、案内・previewのないpracticeを分ける。`recover-after-defense`は受けた当該手には付かず、後の本人の手が受け石を含む三・四を作った場合に付く。未発生は`not-observed`で、成功にも失敗にも換算しない。

限定は残る。幾何学的な二方向、三・四、即五連、次の二つの勝ち口の局所反証を扱う。一般の静かな候補の優劣、数手先の構想の良し悪し、すべてのVCTを指導するわけではない。`unknown`を失敗に変えるべきではないが、未知の局面が続く学習者に、現在の案内だけで適切な改善ができるかは試用で確認する必要がある。

### F2 / F3 — 初見と既知の再現

通常の22課題（今回の再監査中に基本の受け1題を追加）と、通常見本に入らない36確認盤が分離された。`positionFingerprint`は盤全体の回転・反転・平行移動を同一にする。問題IDを替えるだけでは初見に戻らない。開始・失敗・途中放棄も遭遇として残り、ヒント後のclean再入力でも独立確認にしない。

`learning.js:recordLessonView / recordLearningAttempt / getLearningStats`で前回F3の「見本のJ8を見て同じJ8を入力」を再検査する回帰が成功。`firstTryUnaided / familyFirstTryUnaided / independentCompleted`は増えない。`learning-path.js:noteExposure`は進行中の同盤確認を失格にし、完了済みの独立成功は歴史として保つ。appの`exposeLesson / exposeCurrent / markLiveHelp`が台帳へ接続される。

異なるfamilyは著者が決めた判断条件であり、能力の心理測定モデルではない。全盤fingerprintは、無関係な遠方の石だけが変わった実戦の意味的同型まで同定しない。実戦の2局代替は`initialMethod:'practical'`で区別されるが、2family確認と全く同じ一般化範囲を実証したと読んではいけない。

### F4 — 標準の診断と補習

`nextLearningStep`は最初から全見本の閲覧を要求せず、未見診断を出す。初回前の失敗・ヒント・未知・再試行は該当単元の補習へ戻す。補習は支援付きでよいが、補習自体で確認済みにせず、後に未遭遇の別確認を出す。同family1問成功や、相手の応手後の本人着手がない課題で、2family条件を埋めることはできない。

保持は初回確認から24時間以上、別の暦日、新構造盤を要求し、初回の歴史と別に記録する。時間が経っただけでは成功にならず、自動実行も作らない。ただし初回確認後の失敗処理には下記V3-2の反例があった。

### F7 — 自戦からの継続と転用

`app.js:startRecovery`は元棋譜の`ply - 1`までの実手順と、レビューのbefore盤を渡す。`journey.js:config`が一致を確認する。代案を見て一手打つだけで終わらず、白の実応手後も本人が終局まで担当する。元の棋譜は書き換えず、`origin:'review' / role:'recovery' / startPly`で区別する。

最終統合では、レビューで本人が選んで受理された代案を`initialBlackMove`として引き継ぎ、同じ一手をもう一度入力させる状態に戻さずCPU応手へ進める。元のbefore盤・prefix・sourceReviewは保持する。K4を選んだ後、実CPUの白K6が入り、本人の次の判断へ進む画面も確認した。

`reviewStages`は、指摘→合法終局までの復習対局→未見確認（枯渇時は新規実戦2局）→さらに後に始めた別の無補助実戦での当該技能、という段階を持つ。過去の成功、同じ盤の再入力、初回確認以前から進行していた一局、機会なしの一局では後の転用を閉じない。

ただし`recoveryMatches`が認定するのは継続の完了であり、修正成功ではない。元と同じ誤りを繰り返して負けても、合法終局なら次の未見確認へ進める。後段の独立確認と実戦が必要なため、それだけで技能達成にはならない。この区別を維持する必要がある。解析の探索上限やunknownも残り、レビューが全ての序盤・構想ミスを発見するとは言えない。

局面課題の`positionMoves`は開始盤をエンジンに渡す交互のprotocol列であり、本人の実戦履歴ではない。`reviewStartPly`を`scanRecord`が参照し、セットアップ部分を本人の誤りとして評さない。空盤実戦の成績にも入れない。この境界はテストで成立を確認した。

### F8 — 最強CPUに対する実際の測定

`fullGameCheck`が実棋譜を空盤から再生し、途中終局後の着手、占有点、石番の不整合、結果の相違を拒否する。無補助・開始時と終了時の設定一致を要求する。`examEligible`は専用exam role、seriesId、最強、strength100、8000msを追加要求する。既存の普通対局を後でexamに改名できない。

`getExamStatus`の合格は、同じseries内のちょうど10試行が10局とも適格な勝ちであること。投了、中断、補助付きの試行を除いた「都合のよい10勝」を追加しても合格にならない。これは観測された10局全勝を表せる条件であり、今後の無敗保証・棋力認定・最短学習の証拠ではない。投了等の画面集計については下記V3-4を確認する。

### V3-2 — 保持確認の失敗が補習へ戻らない〔優先1・修正を再検証済み〕

根拠: `learning-path.js:unitStatus / nextLearningStep`。

再現: 2026-11-10に`check-priority-gap-a`と`check-priority-options-a`を初見無補助で完了。11月12日の保持確認に選ばれる`check-priority-gap-b`でA1を打つ。実採点結果は`feedback / verifiedMistakes:1`。修正前の単元状態は`initialConfirmed:true, retained:false, needsReview:false, label:'保持待ち'`。priorityを指定しても標準の次はconditionsの初回診断になった。

原因は、失敗に基づく`needsReview`が`!initial`に限定され、標準経路も初回未確認だけを対象とすること。初回成功の歴史を消す必要はないが、後の保持失敗を単なる未受験の待ち状態と混ぜてはいけない。

完了条件: 初回確認後・保持成功後の新たな確認失敗も現在の補習対象にする。失敗後の補習完了を経て、本当に未見の別盤または契約を満たす新規実戦へ進める。古い成功や同盤再入力で新たな失敗を隠さない。

初回後の失敗を無視する元の反例は修正された。新しいpriorityバンクでgap-a＋defend-aを初回完了後、gap-bのA1で失敗すると、`initialConfirmed:true`の歴史を保ちつつ`currentConfirmed:false / needsReview:true / label:'保持の復習'`となり、標準経路は`win-before-block`の補習へ戻る。

追加の確認で、補習後に反対側の`check-priority-defend-b`だけを解いて保持復活する反例も見つけ、再修正した。失敗したのは「黒に五があるので先に勝つ」であり、「黒に五がないので受ける」だけではその再確認にならない。

最終の実API再実行では、`requiredCondition:'own-win-first'`が残り、同側の確認盤が枯渇しているので標準経路は実戦へ進む。反対側のdefend-bを手動で完了しても`currentConfirmed:false / retained:false / needsReview:true`を維持する。同側の新構造別2局が実戦代替になり、miss-win/miss-blockの自戦転用も同じ側で測る。両側を続けて失敗した場合に片側だけを直して他側を隠さない検査、旧成功の再保存・無日時結果で閉じない検査も成功した。

### V3-3 — 標準経路が方向転換を飛ばせる〔優先2・修正を再検証済み〕

根拠: `app.js:startGuidedNext` と `journey.js:journeyTracks.build`。

修正前のcontrollerは、完了したbuild対局の達成を全局で集合化し、`two-directions / build-threat / finish-five`だけを次段階への条件にしていた。trackの必須目標`switch-direction / force-four`や`goalMet`を見ない。したがって、妨害されて構想を修正する機会が一度も発生しなくても進める。

未発生を画面で成功に表示していない点は正しい。しかし、前回F1/F5で欠けていた行為が標準工程の外に残る問題は別にある。

完了条件: 相手による遮断後に本人が残る方向へ進む経験を標準経路で必要とし、自然対局で機会が起きなければ、その事実を保ったまま該当分岐を練習できる。全員を偶然のCPU応手待ちにしない。

修正後は、同じ空盤からの完了勝局で構築・三四・四・五連を観測する。そこで切替が未発生なら`branch`へ進み、横遮断E8/I8と縦遮断H9/H5を各1回、本人が切替→四→五連まで完走する。初回の白応手だけは教材上の条件を実際に成立させる指定手で、それ以後はCPU応手になる。黒が対象形を作らなければ指定手を強要せず自然CPUへ戻す。

`branchOverride`の実白点・blockedAxes・後の本人のswitch証拠をcontrollerが照合する。variantを指定しただけ、未完了、撤回された目標、別局から目標を寄せ集めただけでは進めない。元から空盤対局で全目標を実観測した場合は既知分岐の反復を強制しない。

既知の8石局面からの分岐であること、補助付きであること、本人の空盤実戦ではないことを記録する。したがって成立したのは「自分の空盤構築＋不足した分岐経験の補完」であり、すべての学習者が自作局面の妨害後に独力で成功したとの認定ではない。この区別を含め、実controllerをVMで実行する6テストとjourney APIの検査を再実行した。

### V3-4 — 挑戦集計に投了数が出ない〔優先2・修正を目視まで確認済み〕

根拠: `app.js:renderPracticeLibrary` と `learning-path.js:getExamStatus`。

台帳は`resigned / unfinished / assisted / invalid`を保持するが、修正前の挑戦カードは`resigned / invalid`を表示しない。投了1回の途中挑戦が「0勝・0敗・0分・試行1/10」となる。通常の棋譜一覧には投了が残るため、データを消す不正ではない。しかし挑戦の測定結果として不足する。

完了条件: 投了・無効試行を短い集計で明示し、10局のうち何が完了し、何が不適格だったかを判別できる。説明段落を増やす必要はない。

### V3-5 — 優先判断の2familyが同じ判断側に偏る〔優先2・修正を再検証済み〕

根拠: 修正前の`assessment-bank.js`のpriority4盤。`winningMoves(board, 1)`の件数は順に1、1、4、3。全問で黒の即五連が存在し、目標文も先に五連を作ることを指定していた。`gapped-race / multiple-finishes`は盤の違いとしては実在するが、「黒に今の勝ちがないので白の唯一の完成点を受ける」という判断はpriorityの確認になかった。

修正前にも後のcounter単元には受け四があり、課題対局には`stop-five`があったため、この技能が全教材から欠けていたとは判定しない。しかし、priorityの2family合格を「五と四の優先判断全体」の前提確認として使うには範囲が狭かった。攻守のどちらを優先するかを問う確認には、自分の即勝ちがない対照条件も必要である。これは人間の実験を待たずに確かめられる教材上の不足だった。

完了条件: 初回確認が「自分の五を先に」と「自分の五がなければ相手の五を止める」の両条件を含む、または確認済みという状態の技能範囲を明確に狭め、後者を標準の前提確認で別に扱う。familyの名前や数だけを増やして解決しない。

修正後は`own-win-first`2盤と`prevent-immediate-loss`2盤。新しい`check-priority-defend-a/b`は黒の即勝ち0、白の即勝ち1を持ち、唯一完成点を受ける。実APIで「勝つ条件2盤だけ」「受ける条件2盤だけ」は初回確認不可、両条件なら確認可を確かめた。旧2familyの勝ち記録は同じ`own-win-first`へ正規化され、未経験の守備条件まで昇格しない。

独立した基礎lesson`block-before-building`と3見本フレームも正式単元へ追加された。黒が勝てない盤で白I9の五連を防ぎ、成功表示は「白の五連を止めた」、`claim:'local-goal'`。勝利とは認定しない。見本後にこのlessonを解いても`independentCompleted:0`。この修正に関する2テストも成功した。保持失敗後にどちらの条件を再確認するかはV3-2で別に扱う。

root担当は最終の画面確認で、priorityの確認文が「先に五連を作る/白を止める」と正答側を知らせる問題も修正した。現在は4確認盤すべてのgoalが同じ「黒の一手を選ぶ」。本担当も`getLearningView(createAttempt(id)).goal`を4盤で確認した。lessonでは教える目的に応じて明示し、診断では盤から本人が攻守を判断する。

## 修正で埋める範囲と試用でしか分からない範囲

本監査で具体的に再現したソフト側の残件は解消した。対象は、採点契約、準備の開始条件、保持失敗の補習と同じ判断側の再確認、必須分岐経験、挑戦結果の欠落、優先判断の対照条件と表示漏洩である。この範囲で未修正の重大な反例を残して、人間の試用へ丸投げする判定にはしていない。
